Behavior & implementation boundaries
  • Design proposal, not a live setup screen. All credentials and tasks here are illustrative and held only in memory. Use the example-details buttons; do not enter real secrets.
  • The existing contract provisions users with tasks create-user. Browser setup and the one-time setup key shown here are proposed additions, not existing commands or endpoints.
  • On first load, check setup status before displaying navigation or task content. Show a neutral loading state; failure offers Retry, never assumes the server is empty.
  • Only a server with no users may offer initial setup. Generate a short-lived, single-use setup key for the operator; require it over HTTPS. Never put it in a URL, browser storage, or normal application logs. The exact secure delivery mechanism needs implementation design.
  • Create the first user and consume the key atomically. If another browser finishes first, show “This server is already set up” and offer sign-in. Do not create a second user or silently sign in.
  • After successful account creation, establish a secure HttpOnly session and open a genuinely empty task list. No sample tasks, tutorial checklist, or task editor forced open. Subsequent signed-out visits show sign-in, never initial setup.
  • Keep the browser attached to its current origin. No editable server URL, public registration, profile survey, email verification, or Android updater on web.
  • The phone has a fixed 388 × 862.22 logical screen (9:20) inside a separate proportioned body. Calibration scales the entire device; it does not change wrapping. Viewer preferences alone persist.
